## 1. Project Overview

**What:** Modular business management suite (Odoo-inspired) for a single Indian business.
**Users:** 1–10 users, single tenant. Roles (seeded in `schema.sql`): `admin`, `accounts`, `sales`, `inventory`, `readonly` — each with a per-module `can_read/write/submit/cancel` matrix in `role_permissions`.
**Stack:** React · Node.js/Express · TypeScript · PostgreSQL 16 · Docker Compose (deploy).
**Architecture:** Strict modular monolith. Modules: `core`, `crm`, `sales`, `invoicing`, `accounting`, `inventory`. Each module owns its tables and exposes service interfaces. Cross-module work runs in a single PostgreSQL transaction; domain events handle post-commit side effects.
**Process:** Every phase runs the gstack loop:
`/office-hours` → `/plan-ceo-review` + `/plan-eng-review` → build (Claude Code, mentor mode) → `/review` → `/qa` → `/ship` → `/document-release` → `/retro`

**Starting point:** Existing validated scaffold — PostgreSQL schema (constraints, triggers, seed data), document engine, accounting/inventory/invoicing services, 25-assertion integration suite + concurrency test, `CLAUDE.md` with architectural rules.

---

## 2. Non-Negotiable Invariants (enforced app-level AND db-level)

- Append-only ledgers. Corrections via reversals only — both entries stay posted and net to zero.
- Journal flow: draft → lines → posted (required by trigger architecture).
- Deferred constraint triggers verify journal balance.
- Integer paise everywhere. No floats near money.
- Stock concurrency: ordered `SELECT ... FOR UPDATE`.
- Audit trail: every posting, invoice, and stock move records `created_by` and timestamp.
- No cross-module table access — service interfaces only.

### Phase 1 — Auth, Users & Walking Skeleton
**Duration:** 3–4 weeks · **Status:** 🟡 In progress (backend ahead of plan) · **Target tag:** v0.2

Goal: multi-user auth, the React app shell, and a deployed HTTPS environment — the thin vertical slice.

Note: the auth/RBAC/masters backend was built early alongside the Phase 0 scaffold audit; the frontend shell and deploy remain the bulk of the phase.

Tasks:
- [~] ADR: session vs JWT — **decided: sessions** (argon2id + hashed opaque tokens). ADR file still to be written to `/docs/adr/004-session-vs-jwt.md`
- [x] Users table, password hashing (argon2id), login/logout — *`core/auth.ts`, auth integration test*
- [x] Roles + permission middleware on API routes — *`core/rbac.ts` `requirePermission` guard over the 5-role matrix; RBAC test*
- [x] Audit-trail plumbing: actor propagated through service layer — *`withTransaction` sets `app.user_id` for audit triggers*
- [ ] React app shell: routing, layout, auth guard, design-system baseline
- [~] Admin can create/deactivate users — *`createUser` service exists; no deactivate endpoint or admin UI yet*
- [ ] **Deploy:** VPS + Docker Compose + HTTPS (reverse proxy) + CI/CD push-to-deploy
- [ ] Nightly automated Postgres backup (restore drill deferred to Phase 6)
- [ ] Harden: helmet, rate limiting on `/auth/*`, CSRF tokens (per system-design §6)

Exit criteria: two users with different roles log in on the **live URL**; a restricted role is blocked from admin routes; unauthenticated API calls rejected; every mutation records who did it.

Legend for checkboxes: `[x]` done · `[~]` partially done · `[ ]` not started.

### Phase 4 — Sales, Invoicing & GST
**Duration:** 4–5 weeks · **Status:** 🔲 Not started · **Target tag:** v0.5

Goal: quotation → order → GST invoice → payment, fully posted. Highest-risk phase (tax correctness, not code).

Tasks:
- [~] Customer master (GSTIN, state code, billing/shipping) — *`crm/companies` CRUD service + routes already built (customer/supplier flags, gst_treatment, GSTIN validation, billing/shipping); UI pending*
- [ ] Quotation builder (reuse QuoteFlow patterns where sensible)
- [ ] Quotation → sale order conversion
- [ ] Invoice generation: CGST/SGST vs IGST by place-of-supply, HSN lines, rounding rules
- [ ] Invoice → journal posting; invoice → stock deduction (single transaction)
- [ ] Invoice PDF (GST-compliant format)
- [ ] Payment recording + outstanding/receivables view
- [ ] **GST validation:** reproduce ≥5 real past invoices from the business and match totals exactly

Exit criteria: end-to-end dummy transaction (quote → invoice → payment) reflected correctly in ledger AND stock; real-invoice reproduction test passes; UAT sign-off from the business.

### Phase 5 — CRM
**Duration:** 2–3 weeks · **Status:** 🔲 Not started · **Target tag:** v0.6

Goal: leads and pipeline. Deliberately last — fewest invariants, lowest risk.

Tasks:
- [ ] Leads: create, assign, stages (kanban or list)
- [ ] Activities/notes on leads
- [ ] Lead → customer conversion; lead → quotation handoff

---

### Phase 6 — Production Hardening
**Duration:** 2–3 weeks · **Status:** 🔲 Not started · **Target tag:** v1.0

Goal: the system survives failure, and operating it is documented.

Tasks:
- [ ] **Restore drill:** destroy staging server, restore from backup, verify zero ledger corruption
- [ ] Structured logging + error tracking (e.g. Sentry or equivalent)
- [ ] Basic monitoring/uptime alerting
- [ ] Security pass: gstack `/cso` audit (OWASP), dependency audit, rate limiting
- [ ] Runbook: deploy, backup/restore, common incidents, onboarding a user
- [ ] Data migration path: import the business's opening balances + masters
- [ ] Final UAT across all modules with real users

Exit criteria: restore drill passes; runbook lets a stranger operate the system; real opening data loaded; v1.0 tagged.
